## Server tools

*Written 2026-09-24 for `SkyWynn-Server-Setup-Plan.md` and `research/Settings-Spec.md` (the admin config editor is the twin of the player Settings registry already speced there). Question asked: how do other games/servers let owners set things up IN GAME, so SkyyMenu's "Mods" section and the bigger per-feature editors (NPC shops, NPC quests, ranks) can borrow the parts that work and dodge the parts that don't.*

### 1. Settings-panel layout patterns (categories, search, value widgets, reset, confirm)

- **BentoBox** (the Minecraft skyblock framework SuperiorSkyblock2 competes with) ships two parallel panels off the same renderer: a per-island **player** settings panel and a world-wide **admin** settings panel (`/[admin] settings`), both built from the identical panel engine — the admin one just points at different flags (global defaults, whether a flag is even visible to players) rather than being a bespoke page. VERIFIED (docs + GitHub). As of a recent BentoBox 2.0 pull request, both panels became **template-driven**: the whole layout (which flag goes in which slot, icon, order) lives in a YAML file server owners can edit without touching Java, separate from the flag's own logic. UNVERIFIED exact YAML shape (docs page didn't spell out widgets/search/confirm), but the split itself — "panel layout" as one file, "what a flag does" as another — is a pattern worth copying: SkyyMenu's page renderer and each mod's `regSetting(...)` calls already do this split (section 1.2 of Settings-Spec.md), so this is a confirmation, not a new idea, for us.
- A dedicated **ControlPanel** add-on for BentoBox goes further: it lets a server owner build an entirely custom clickable menu from one YAML file, with icons, multiple click actions per button, and live placeholders, with zero Java. VERIFIED. Read for us: even after SkyyMenu's shared editor exists, a server owner might still want to hand-pick which dozen settings appear on a single "quick config" front page rather than paging through every category — worth keeping in mind as a stretch goal, not for this round.
- **Hypixel SkyBlock's** player Settings menu (already the base of `Settings-Spec.md`) is the strongest categorized-click-menu precedent: a menu item opens tabs by game area (Personal, Comms, Island, API…), each tab is a scrollable grid of ON/OFF rows. VERIFIED (cross-checked prior session, restated here for context). The admin-menu genre borrows the exact same shape (tabs = categories, rows = individual switches) rather than inventing a new one — good sign that our plan to reuse the player Settings page's tab/row layout for the admin Mods config page is the well-worn path, not a shortcut we're inventing.
- **Authority Admin** (a generic Minecraft "admin panel GUI" plugin) stores its whole menu layout — button positions, icons, label text, which permission node gates each button — in one `menus.yml`, so a server owner can rewrite, hide or re-permission any button without recompiling or touching Java. VERIFIED (product description). This is the same idea as BentoBox's template panel: **the page layout is data, not code**, so re-skinning or trimming a panel is a text edit, never a rebuild. Directly useful for SkyyMenu: since our page code is itself generated by a Python build script (no live "menus.yml" today), the equivalent for us is what Settings-Spec.md already does — mods register rows at runtime through the bridge rather than hard-coding them into SkyyMenu's Java, so a mod can add/remove a setting without a SkyyMenu rebuild.
- **Common mechanical details across every "settings GUI" example found** (BentoBox, SuperiorSkyblock2, Hypixel, generic admin panels): a row shows label + current value + an action to change it (click-to-cycle for booleans/enums, a chat-prompt or typed-value box for numbers/text), and a **reset-to-default** action per row or per page is standard enough that its absence is what players/owners complain about in threads. No source described a "type a value directly in the GUI" numeric text field the way our TextField + `@Key`/`#Id.Value` + rebuild pattern can do — most Bukkit-era plugins fall back to "click, then type your answer in chat" because Bukkit inventory GUIs can't take real text input. That's a spot where Hytale's inline UI (real TextField) can beat the reference plugins outright: a number or item-id setting can be edited in the page itself, no chat prompt needed.
- **Confirm-before-apply for dangerous values**: no single reference plugin was found with a generic "this could break your server, type YES" dialog built into a settings GUI — the pattern search engines returned instead was **rollback plugins catching the damage after the fact** (see Audit logs below), not prevention. The one closest "confirm" pattern is LuckPerms' web editor (below): it never applies anything live — every edit becomes a **generated command you must run yourself**, which is itself a confirm step. Read for us: since nothing in the wild does real pre-apply confirmation well, a simple two-click "Change X from A to B? [Confirm] [Cancel]" page for numeric/economy values (death penalty %, bazaar fee %, XP multipliers) would be ahead of the genre, not behind it, and cheap to build with our existing rebuild-on-click pattern.

### 2. NPC shop editors: the config-file vs. fully-in-game split

- **Shopkeepers** (Bukkit): sneak + right-click an NPC shopkeeper to open its editor — a chest-style GUI where the top row is "what this shopkeeper sells" (drag items in) and the bottom row is editor-only buttons (change price, change the mob/skin, toggle admin-vs-player-stocked). VERIFIED. Everything is done by clicking on the live NPC; no config file editing needed to run a shop day-to-day. Two shop kinds exist: **admin shops** (infinite stock, price set by the owner) and **player shops** (stock pulled from a real chest the player placed, so the shop can run dry) — a distinction directly relevant to Skyy's still-open "buy-only or also sell-to-NPC, limited stock, restock timer" question in `SkyyEconomy-Plan.md`: Shopkeepers' answer is admin shops never restock because they're infinite, and restocking is literally a player refilling their own chest.
- **ShopGUIPlus** vs **EconomyShopGUI** is the cleanest "config file vs. in-game" contrast found this session, for the *catalog* (not per-NPC) style of shop, i.e. one `/shop` command opening a big categorized item catalog rather than many placed NPCs. ShopGUI+ is mainly edited through config files uploaded to the server (add an item = edit a YAML, then reload). EconomyShopGUI's stated selling point is the opposite: items, prices and whole categories can be added/edited/removed with in-game commands alone, with **no config file edit and no server restart** needed for the change to take effect. VERIFIED (both plugins' own marketing copy, consistent across multiple listing sites). Read for us: this is exactly the trade-off Skyy is already steering SkyWynn away from (config files as the *only* path) — EconomyShopGUI is proof the config-file-only shops lost the popularity contest to the in-game-editable one, which validates the whole "in-game server setup" direction, not just for shops.
- Neither shop plugin's docs mentioned a **search box** inside the shop-editing GUI itself (only inside the player-facing buy menu, to find an item to purchase) — editing/adding a shop item is still done by holding the item and running a command or dragging it into a slot, not by typing its name. That's a gap our NPC shop editor could close cheaply since we already have working inline TextField search (SkyySacks 0.7.3's search box, confirmed working in game): a shop-editor page that lets an admin type a partial item name to find what to stock, instead of needing the item physically in hand, would be a small improvement over both reference plugins.

### 3. NPC quest editors: the cautionary tale

- **BetonQuest** (the deepest Minecraft quest-scripting plugin, conversation trees + conditions + events) explicitly does **not** have a real in-game GUI editor for building quests, and its own team has said so directly: quests are complex enough that trying to author them through chat prompts and inventory clicks was judged not workable, so the *intended* fix was always an external desktop tool that connects to the server, not an in-game menu. VERIFIED (project's own GitHub discussion). An old community "BetonQuest-Editor" desktop app existed for a 2017-era version and is explicitly marked end-of-life/unmaintained; a Forge client-side "GUI" mod exists but talks to the Spigot plugin from outside vanilla's own UI, i.e. still not "click a menu in the game you're playing." This is the strongest signal in this research round: **once a quest system's logic gets past "give item / kill mob / go here," pure in-game editing (chat + inventory clicks) stops being the right tool**, and the mature answer people reach for is a *separate structured editor*, not a deeper GUI.
- **Quests (PikaMug)**, aimed at being the easy/approachable alternative to BetonQuest, does the opposite bet and mostly wins it for its target audience: nearly the whole quest — objectives, rewards, requirements — is set up by answering prompts **in chat** while running an in-game creator command, and simple quests can be built end-to-end without leaving the game or touching a file. VERIFIED (project's own docs). It hooks Citizens (or ZNPCsPlus) NPCs as quest-givers by pointing the creator at an existing NPC rather than having its own separate NPC system. Read for us: this maps well to Skyy's stated goal ("NPC quests… editable in game") *for the kind of quests SkyWynn's story beats likely need* (deliver item, kill mob count, reach a location, talk to NPC) — chat-prompt-driven or, better for us, a page-driven step-by-step builder (we don't need to fall back to chat since we have real TextField input) should cover the common cases. The BetonQuest lesson says: don't promise a fully in-game editor will handle *arbitrary* branching dialogue trees or scripted conditions forever — plan for an escape hatch (raw JSON/property file editing, or a later desktop-style tool) once quest logic outgrows "linear steps + rewards," the same way BetonQuest's own team concluded.
- **Citizens** itself (the NPC framework both quest plugins build on) is command/chat-first at its core (`/npc create`, `/trait <name>`, then follow chat prompts per trait), and a real point-and-click editor GUI is a *separate, third-party add-on* (CitizensGUI: sneak + right-click an NPC, or `/npcgui`) rather than something Citizens ships itself. VERIFIED. The split mirrors what we already do differently and better: our menu-driven NPC editor (planned as part of SkyyEconomy's NPC shops and the future SkyyQuests) can be first-class and native instead of a bolt-on, since we're not working inside vanilla Bukkit's chest-GUI limits.

### 4. Ranks and permissions: LuckPerms' "edit safely, then commit" pattern

- **LuckPerms**, the standard Minecraft permissions manager, does *not* let you free-edit permissions live in a chat menu. Running `/lp editor` (or `/lp user <name> editor`) spins up a **temporary web session**: the server prints a link and a one-time code, the owner opens it in a browser, edits groups/permissions/prefixes/weights/inheritance visually, and clicking **Save** doesn't silently apply anything — it hands back a **command to paste into the server console or in-game**, which is what actually commits the change. VERIFIED (project's own wiki, consistent across multiple guides). Groups form an inheritance chain (e.g. `admin` inherits `vip` inherits `default`), which is also the shape every "staff hierarchy" guide recommends for rank ladders (Helper → Mod → Admin → Co-owner → Owner, each inheriting the one below plus its own extra nodes). VERIFIED (multiple independent hosting/guide sites agree on this ladder shape, though the exact rank *names* vary site to site — treat the ladder concept as solid, the specific names as just an example).
- Read for us: LuckPerms' "prepare changes somewhere safe, only commit with an explicit final action" is a genuinely different (and safer) shape than a straight live-edit page, and it's the closest thing found this session to a real "confirm dangerous changes" mechanism in a widely-used tool. We don't need a separate web app to copy the *idea* — the equivalent for SkyyMenu's admin config page is what section 1's "no source does real pre-apply confirmation well" note already suggests: build a lightweight two-step commit (edit, then a separate Confirm click) at least for anything that touches money, permissions, or ranks, even though most of our simple ON/OFF settings can safely stay single-click like the player Settings page.
- General guidance repeated across staff-hierarchy write-ups, independent of any one plugin: keep the number of people with the *highest* rank (full admin/owner-level access, able to touch economy and permissions) very small on purpose, and give most staff a narrower rank scoped to moderation only (mute/kick/ban, not economy or config). That argues for our ranks/permissions editor treating "who can open the Mods/config section at all" as its own separate, more sensitive permission from "who can moderate chat or players" — not one blanket "staff" flag.

### 5. Server admin menus: EssentialsX, and Hytale's own admin mods (closest precedent)

- **EssentialsX** used to require hand-editing `kits.yml`/config files to add a kit; a more recent version added the ability to **create a kit from in-game** and have it show up without a manual file edit or reload. VERIFIED (project's own wiki "Improvements" page). Small example, same direction as everything else in this research: even an old, config-file-first plugin is moving features from "file only" to "in-game, file still exists underneath" over time — validates Skyy's rule ("config files stay… game and files always agree") as the way the wider ecosystem is trending anyway, not a novel idea we're taking a risk on.
- **Hytale-specific precedent (most directly relevant find this session):** at least three admin mods already exist for Hytale on CurseForge doing a version of exactly what SkyyMenu's Mods section wants to become — **AdminUI** and **Admin Panel** both open a single `/admin` command into a multi-module dashboard (whitelist, bans, mutes, warps, live server stats, backups, word filter), with per-module permission nodes (e.g. `AdminUI.ban.open`) rather than one all-or-nothing admin flag, and settings/mute/filter data persisted to JSON files that survive restarts. **EliteEssentials** for Hytale bundles homes/warps/kits/economy/bans/mutes/warnings/admin UI/chat formatting into one mod with SQL storage. UNVERIFIED whether any of the three apply every change live with zero restart (their store pages don't say either way), and none of their descriptions mention an audit log, export/import, or a settings-registry-style "any mod can plug a new row into the same page" architecture — which is exactly the gap `SkyWynn-Server-Setup-Plan.md`'s shared-editor idea (one registry, any mod plugs in) would fill that the existing Hytale admin mods don't appear to have. Read for us: the market already validates "one `/admin` (or Menu) entry point, many module panels, per-module permission nodes, JSON persistence" as the right shape *for Hytale specifically* — SkyyMenu's plan matches this, and the shared-bridge-registry piece (any Skyy mod can register a settings page without SkyyMenu needing a rebuild) would be a genuine step ahead of what's publicly available for this engine today.

### 6. Audit logs, rollback and "undo" for admin/config mistakes

- **CoreProtect**, the most widely installed Minecraft logging/rollback plugin, logs essentially every world-changing action (block break/place, chest transactions, chat, commands, sign edits, logins, item drops) to a local database with almost no configuration required to start — VERIFIED, and its own selling point is precisely that near-zero setup means less to misconfigure. Rollbacks support a **`#preview`** flag that shows what a rollback *would* undo before committing, plus an explicit **`/co undo`** to undo the undo, and `/co restore` to redo it. VERIFIED (project docs).
- **CraftAudit** and **AuditTrail** are the same idea for Forge-side/other setups: log every change, allow area/time-scoped queries, and support rollback/restore, with **UltimateLogger**-style plugins adding a GUI log *viewer* on top of the raw command output. VERIFIED (existence and stated features; not independently cross-checked beyond their own listings, so treat feature lists as UNVERIFIED in detail).
- None of these tools are *config-editor* audit logs (who changed which setting from what to what) — they're all *world-state* audit logs (who broke/placed/stole what). That gap matters for us: `SkyWynn-Server-Setup-Plan.md` already calls for "every change logged (who, when, old → new value)" for the *settings* editor specifically, and nothing found this session does that well for plugin settings the way CoreProtect does it for blocks — it's a place SkyyMenu's admin editor can be ahead of the reference tools rather than just catching up, and it should be cheap: append one line per `settings:fn:set` call (who, key, old, new, when) to a simple log file, same shape as the existing `WARNED`/one-time-log pattern already used in `SetReg`.
- **Read for us on "the mistakes server owners hit"**: the recurring failure mode across every source touching this topic isn't a plugin *lacking* rollback — it's a bad value going live with **no preview and no easy revert**, discovered only after players are already affected (an economy number typo'd 10x too high, a duration field parsed wrong). CoreProtect's `#preview`-before-commit and LuckPerms' edit-then-generate-a-command-to-commit are the two concrete "look before you leap" patterns found; a reset-to-default button (present in essentially every settings-panel plugin surveyed) is the fallback once a bad value *is* live. Our settings registry already has defaults wired in (`SetReg.def`), so "reset to the registered default" is nearly free to add to every row in the admin editor, and is worth treating as a required part of the page, not a nice-to-have.

### 7. Export / import of a setup

- No Minecraft plugin found this session does a clean one-click "export my whole server's plugin config, import it on a fresh server" for *plugin settings* specifically — the closest is **MCPM**, a third-party Minecraft plugin *package manager* with `export`/`import` commands for reproducing a whole plugin+config setup on a new server, and a client-side mod ("Easy Configs") that zips up client **mod** configs to share between players. Both are UNVERIFIED beyond their own project descriptions (small/niche projects, single-source). The practical norm across the ecosystem is much lower-tech: server owners just copy the plugin's own config/data folder to a new server wholesale, because most plugins already store settings as plain files. Read for us: this is actually good news for SkyWynn's architecture — because every Skyy mod already writes to `Skyy_<Mod>/*.properties` files rather than one giant world save, "export a setup" for us can be as simple as zipping the relevant `Skyy_<Mod>` folders (which `SkyWynn-Server-Setup-Plan.md` already lists as a wanted feature — "export/import a mod's whole config as a code or file"), which is more than most of the reference ecosystem bothers to offer as a first-class feature.

### Summary of ideas worth carrying into the SkyyMenu admin editor spec

1. **Split layout from logic**, the way BentoBox's template panel and Authority Admin's `menus.yml` do — we already do this via the bridge registry (`Settings-Spec.md` section 1.2); keep doing it for the admin editor so a mod can add a config row without a SkyyMenu rebuild.
2. **Real typed-value editing** (our TextField pattern) beats every Bukkit-era reference plugin's "click, then answer in chat" fallback — lean into it for numeric/text settings instead of copying the chat-prompt pattern.
3. **Reset-to-default per row**, present in nearly every reference settings panel and nearly free for us since `SetReg.def()` already exists — should be a required element of every admin settings row, not optional polish.
4. **A lightweight "edit, then confirm" second step** for money/permission/rank-affecting values, inspired by LuckPerms' edit-then-generate-a-command flow, since no reference tool does true pre-apply confirmation well and we can be ahead of the genre cheaply.
5. **A real settings-change audit log** (who/when/key/old/new) — this genre has excellent *world* audit logs (CoreProtect, CraftAudit) but nothing found here does the same for plugin *settings*; a simple append-only log fits our existing one-time-log style already used in `SetReg.WARNED`.
6. **NPC shops**: admin shops = infinite/no restock, player-style shops = pull from real stock that can run dry (Shopkeepers' split) answers Skyy's open restock question cheaply; add item search-by-name to the shop editor (something no reference shop plugin's editor offers) since we already have a working inline search field.
7. **NPC quests**: build the in-game step-by-step editor for the common cases (item turn-in, kill count, reach location, talk to NPC — PikaMug Quests' territory), but plan an escape hatch (direct file/JSON editing) for anything more complex, because BetonQuest's own team concluded pure in-game editing stops scaling once quests get branching logic, and we shouldn't promise otherwise.
8. **Ranks/permissions**: keep the number of people with full admin/config access small by design (near-universal advice across staff-hierarchy guides), and treat "can open Mods/config" as a separate, narrower permission from general moderation — don't fold them into one "staff" flag.
9. **Export/import**: cheap and already fits our architecture — zip the relevant `Skyy_<Mod>` data folders; nothing in the wild does this better than what our own per-mod file layout already allows.
10. **Hytale's own admin mods (AdminUI, Admin Panel, EliteEssentials)** already prove the "/one command → many module panels → per-module permission nodes → JSON persistence" shape works well on this exact engine — the gap they leave open, and where SkyyMenu's shared-registry plan is already ahead, is a single settings registry any mod can plug into plus a real change log — neither appears to exist in the public Hytale admin-mod space yet.

## Engine

*Written 2026-09-24 for `SkyWynn-Server-Setup-Plan.md` (the admin config editor is the twin of the player Settings registry in `Settings-Spec.md` sections 1.1-1.5: same bridge-Function-with-Object[]-of-java.lang-types idea, same load-order-fallback keys, same never-throws/atomic-write-on-the-scheduler rules). Read-only session: no build script, jar, mod folder or server file was touched. Everything below is a class/method-name inventory from `tools/dev/reflect.py`, `bc.py` and `cpgrep.py` run against the real `HytaleServer.jar`, plus `reflect.py` run against a few installed third-party mod jars (class/method NAMES only — no method body was copied, per Skyy's clean-room rule; "reference only" throughout section 4 and the Action/Builder note in section 3). Tags: **VERIFIED** = seen directly this session in a class's reflected signature, in disassembled bytecode, or in a real on-disk save file. **UNVERIFIED** = inferred, not directly observed — needs an in-game test.*

### 1. Permission system (`HytaleServer.jar`)

**Groups and "op".** The real provider is `com.hypixel.hytale.server.core.permissions.provider.HytalePermissionsProvider` (`extends BlockingDiskFile implements PermissionProvider`). Its constants, read live this session (VERIFIED, exact values): `GROUP_NONE="hytale:None"`, `GROUP_ADVENTURER="hytale:Adventurer"` (= `DEFAULT_GROUP`, what every new player starts in), `GROUP_BUILDER="hytale:Builder"`, `GROUP_WORLD_EDITOR="hytale:WorldEditor"`, `GROUP_SERVER_EDITOR="hytale:ServerEditor"`, `GROUP_ADMIN="hytale:Admin"` (= `OP_GROUP`). **"Op" is nothing but membership in the `hytale:Admin` group** — confirmed byte-for-byte by disassembling `com.hypixel.hytale.server.core.permissions.commands.op.OpAddCommand#executeSync` (the real vanilla `/op add <player>` handler): it calls `PermissionsModule.get().getGroupsForUser(uuid).contains("hytale:Admin")` to check "already op", then `PermissionsModule.get().addUserToGroup(uuid, "hytale:Admin")` to grant it. Sibling commands: `OpCommand` (root, an `AbstractCommandCollection`), `OpRemoveCommand` (`removeUserFromGroup` equivalent), `OpSelfCommand` (an `AbstractPlayerCommand` — a player-run `/op self ...`, presumably singleplayer/LAN self-service; not decompiled further).

**Storage.** `PERMISSIONS_FILE_PATH = "permissions.json"`, one **per world/save folder** (VERIFIED: every folder under `Saves\<world>\` on this machine has its own, not one global file — op/ranks are per-world). Schema, read from 10 real save files this session: `{"users": {"<uuid>": {"groups": ["hytale:Admin", ...]}}, "groups": {"<name>": {"parent": "<parentName>", "permissions": ["node", "*", ...]}}}`. A second, older-looking shape also parses fine (`"groups": {"<name>": ["node", ...]}`, a bare array — `HytalePermissionsProvider.read()` accepts both). **Non-`hytale:*` group names already exist on disk** (`"OP"`, `"Adventure"`, `"Default"`, `"default"` — created by other already-installed mods on this machine calling the API below), so groups are open, not a closed vanilla enum: **a plugin can add its own groups/ranks**, confirmed both by the API (`addGroupPermission` below creates the group if new) and by this on-disk evidence.

**Read/change a player's groups and a group's permissions at runtime.** `com.hypixel.hytale.server.core.permissions.PermissionsModule` (a `JavaPlugin`, singleton via `static PermissionsModule get()`). VERIFIED method list (reflect.py):
- `Set getGroupsForUser(UUID)` / `void addUserToGroup(UUID, String)` / `void removeUserFromGroup(UUID, String)` / `void setUserGroup(UUID, String)` (replaces the whole group set with one group)
- `void addGroupPermission(String group, Set nodes)` / `void removeGroupPermission(String, Set)` — creates the group if it doesn't exist yet
- `void addUserPermission(UUID, Set)` / `void removeUserPermission(UUID, Set)` / `boolean hasUserGrant(UUID, String)` (a node granted directly to a user, bypassing groups)
- `boolean hasPermission(UUID, String)`, `hasPermission(UUID, PermissionQuery[, boolean])`, plus static `hasPermission(Set<String> groups, String|PermissionQuery)` for a raw group-set check
- `Set getAllRegisteredGroups()`, `Set getUsersWithPermission(String)`, `void reload()` (re-reads `permissions.json`), `Map getVirtualGroups()`
- Change events exist to listen instead of poll (VERIFIED classes): `com.hypixel.hytale.server.core.event.events.permissions.PlayerPermissionChangeEvent` (+ inner `.GroupAdded` / `.GroupRemoved` / `.PermissionsAdded` / `.PermissionsRemoved`) and `GroupPermissionChangeEvent` (+ `.Added` / `.Removed`).
- Read side for a page/command: `PermissionHolder` interface (implemented by `PlayerRef`) — `boolean hasPermission(String)` / `hasPermission(PermissionQuery[, boolean])`. This is the exact call already used inline in shipped Skyy code (`pr.hasPermission("skyycollections.admin")` in `tools/coll_0_1_3_patch.py` / `coll_0_1_4_patch.py`, `pr.hasPermission("skyycooking.admin")` in `tools/cooking_0_1_1_patch.py`).

**How a command's permission check actually runs** (bytecode-verified this session against the current jar; matches and confirms the reasoning already written into `tools/bazaar_0_1_1_patch.py`, `tools/coins_0_1_4_patch.py`, `tools/party_0_1_2_patch.py`, `tools/islands_0_4_3_patch.py` from earlier build rounds — nothing new invalidates that prior work):
1. `AbstractCommand.setPermissionGroups(String[])` records which permission GROUPS should get the command's own auto-generated node; it does nothing live by itself.
2. At boot, `CommandManager.createVirtualPermissionGroups()` walks every registered command's `getPermissionGroupsRecursive()` — bytecode confirms `AbstractCommand.putRecursivePermissionGroups(Map)` recurses into `getSubCommands()` only (never `getVariantCommands()`) — building `Map<permissionNode, Set<group>>`, handed to `PermissionsModule.setVirtualGroups(Map)`. This is what lets `hytale:Adventurer` run `/bazaar` etc. with no real `permissions.json` entry for that node.
3. `AbstractCommand.hasPermission(CommandSender)` — bytecode confirmed this is exactly `sender.hasPermission(PermissionQuery.of(getPermission()))`. `getPermission()` is filled in once by `setOwner()` via `generatePermissionNode()` (`String.toLowerCase(Locale.ROOT)` of the base permission + command name) unless `requirePermission(String|PermissionQuery)` set it explicitly, or `requireNoPermission()` opened it to everyone.
4. Established (and now bytecode-reconfirmed) Skyy pattern: player-usable commands call `setPermissionGroups(new String[] { "hytale:Adventurer" })`; admin-only commands/subcommands call `requirePermission("modname.admin")` **and** `setPermissionGroups(new String[0])` so the subcommand does not also inherit the parent's Adventurer grant (an explicit, even empty, group list on a subcommand wins over inheriting the parent's). `HytalePermissions` (constants class): `NAMESPACE="hytale"`, `COMMAND_BASE="hytale.command"` — confirms our own `skyyxxx.*` nodes deliberately live outside the engine's own namespace.

**Chat prefixes / colours per rank — not a built-in field.** `HytalePermissionsProvider$GroupData` (a Java record) carries only `parent` and `permissions` — no prefix/colour/weight field anywhere on a group. The engine will not hand us a rank's display prefix; a future ranks mod has to store that itself and apply it in a chat hook. The hook point already exists and is proven: SkyyExploration's chat handler registers `EventRegistry.registerAsyncGlobal((short) 30000, PlayerChatEvent, Function)`, above `EventPriority.LAST` (21844) (VERIFIED, `SkyyExploration/build_skyyexploration_0.1.py`). A ranks mod can do the same (or hook slightly lower-priority) and look up `PermissionsModule.get().getGroupsForUser(uuid)` — or its own rank map, since the group itself carries no prefix — to prepend a prefix before the message is finalized.

### 2. "Is this player an admin?" — safe check inside a page handler

Every Skyy `CustomUIPage`/`InteractiveCustomUIPage` is a **per-open instance** that keeps the opening player on a field for its whole lifetime (VERIFIED: SkyyMenu's `MenuPage` keeps `this.playerRef`, referenced throughout `SkyyMenu/build_skyymenu_0.1.3.py` for purse/bank/warp lookups, and even to run another mod's command as that player: `CommandManager.get().handleCommand(this.playerRef, "cmd args")`, gated first by `c.hasPermission(this.playerRef)` — wrapped in `try { ok = c.hasPermission(this.playerRef); } catch (Throwable t) { ok = false; }` even though the method can't throw, matching the project's belt-and-braces "never throws" style).

Recommended pattern for the new admin config editor — no new engine API needed, just the existing call, inline in the click handler:
```
if (!this.playerRef.hasPermission("skyymenu.modconfig")) { this.status = "..."; rebuild(); return; }
```
(same shape as `pr.hasPermission("skyycollections.admin")` / `pr.hasPermission("skyycooking.admin")` already shipped). Grant the node once at setup with `PermissionsModule.get().addGroupPermission("hytale:Admin", <set containing "skyymenu.modconfig">)` — going straight to `PermissionsModule`, not through a command's virtual-group path, since a page click (not a command) is being gated. Checking the node rather than `getGroupsForUser(uuid).contains("hytale:Admin")` directly is deliberately safer: it still respects a server owner who re-granted (or revoked) that node on a different/custom group, same reasoning as every existing `skyyxxx.admin` gate. **Re-check on every sensitive click, not just on page-open** — a still-open page instance does not mean the player is still an admin (their rank could change mid-session); gate both "show the Mods entry at all" and each button inside it.

### 3. NPCs (for a future shop/quest editor)

Hytale ships a full data-driven NPC framework under `com.hypixel.hytale.server.npc.*` (plugin `com.hypixel.hytale.server.npc.NPCPlugin`), plus a lighter path a plugin can call directly. Both VERIFIED by class reflection this session (method bodies were not decompiled beyond bytecode call-lists for one vanilla command, to confirm the call chain — no logic copied).

- **Spawn — simple path (recommended for SkyyEconomy's NPC shops).** `NPCPlugin.get()` (singleton) exposes: `boolean hasRoleName(String)` and `List getRoleTemplateNames(boolean)` to find an existing NPC "role" template already shipped in the game's assets (villagers, traders, etc. — "steal what already works" instead of inventing a new mob/model), then `Pair spawnNPC(Store, String group, String roleName, Vector3dc pos, Rotation3fc rot)` to spawn one by name, or `SpawnTestResult spawnNPCWithSpaceValidation(Store, String, String, Vector3dc, Rotation3fc[, TriConsumer[, boolean, boolean]])` for the same with a room check first (compare the result to the static `SpawnTestResult.TEST_OK`).
- **Spawn — the vanilla `/npcspawn` command's own (heavier) path**, traced via `bc.py` on `NPCSpawnCommand#execute` for reference: `BuilderInfo.getIndex()` → `NPCPlugin.forceValidation(int)` → `testAndValidateRole(BuilderInfo)` → `tryGetCachedValidRole(int)` → build a `SpawningContext`, `.setSpawnable(...)`, `.set(World, x, y, z)`, require `ISpawnableWithModel.canSpawn(...) == SpawnTestResult.TEST_OK` → `NPCPlugin.spawnEntity(Store, int builderIndex, Vector3dc, Rotation3fc, Model, TriConsumer)`. The by-name `spawnNPC(...)` above is the friendlier equivalent for a plugin; prefer it over reimplementing this chain. Underlying primitive both paths bottom out on: `World.spawnEntity(Entity, Vector3d, Rotation3f)` / `World.addEntity(Entity, Vector3d, Rotation3f, AddReason)` on `com.hypixel.hytale.server.core.universe.world.World` — go through `NPCPlugin`, not this directly, since role/model/AI wiring lives there.
- **Make it interactable — the cheap route.** `com.hypixel.hytale.server.core.event.events.ecs.UseEntityEvent` (an `EcsEvent`) fires whenever a player uses/right-clicks ANY entity, independent of the heavier asset system below. `UseEntityEvent$Pre implements ICancellableEcsEvent` (`isCancelled()`/`setCancelled(boolean)`) exposes `getTargetEntity()` (a `Ref`), `getContext()` (`InteractionContext`), `getInteractionType()`. Listening for this globally, matching `getTargetEntity()`'s underlying UUID against our own saved set of shop-NPC UUIDs, cancelling on a hit and opening our own `CustomUIPage` is the lightweight route — no JSON asset authoring needed.
- **The engine's "proper" extension point is heavier** — seen in two installed third-party mods this session, reference only, no code copied (Skyy's clean-room rule): a custom NPC behavior is an `Action`/`Builder`(/`Validator`) triple plugged into the asset pipeline. `com.zbeve.roguetale.npc.ActionOpenShop extends com.hypixel.hytale.server.npc.corecomponents.ActionBase` (`boolean execute(Ref, Role, InfoProvider, double, Store)`, `boolean canExecute(...)`) paired with `com.zbeve.roguetale.npc.BuilderActionOpenShop extends com.hypixel.hytale.server.npc.corecomponents.builders.BuilderActionBase` (`Action build(BuilderSupport)`, `Builder readConfig(JsonElement)` — an NPC's behavior-tree JSON asset references the builder by id, and `readConfig` parses its JSON block). `MajorDungeons-0.4.13.jar` does the same shape for its barter shops (`com.danbagh.dungeonframework.features.npc.ActionOpenTabbedBarterShop` / `.builders.BuilderActionOpenTabbedBarterShop` / `.TabbedBarterShopExistsValidator`, plus `events.NPCRegistrationSystem`, an ECS system that appears to track/re-attach spawned dungeon NPCs). This route needs real JSON asset authoring and `BuilderCodec`-based registration at setup — a much bigger lift under javassist (no generics/lambdas/anonymous classes) than the `UseEntityEvent` route. **Recommendation: use `spawnNPC` + `UseEntityEvent` for SkyyEconomy's NPC shops; only reach for the Action/Builder asset route later if an NPC also needs to fight, wander, or run vanilla AI.**
- **Save/restore across restart.** Neither route above needs a bespoke entity-persistence system: a spawned world entity is already part of normal world/chunk save data (the same mechanism keeping every mob and player alive across a restart) and keeps a stable UUID (`World.getEntity(UUID)` / `getEntityRef(UUID)`, the same accessor shape already relied on for `PlayerRef`). What OUR mod must persist itself is the mapping from that UUID to our shop config (items/prices/stock) — a plain file keyed by UUID, same shape as every other Skyy per-entity save file. **UNVERIFIED, needs an in-game restart test:** whether a `spawnNPC`-spawned entity keeps identical AI/role wiring for free, or needs re-spawning on load — `NPCPlugin.onNPCsLoaded(AllNPCsLoadedEvent)` exists as its own hook distinct from generic entity/chunk load, which suggests NPCs may have a separate load pass worth re-attaching to rather than assuming "it just works."
- **Remove.** No NPC-specific despawn method was found yet beyond the generic `com.hypixel.hytale.server.core.event.events.entity.EntityRemoveEvent` class (exists, not reflected in detail) — open item for a follow-up pass once the spawn path above is tested in game.

### 4. Installed mods with an in-game config UI (class/method-name inspection only; nothing decompiled beyond signatures, nothing copied)

- **`HyperEssentials-0.1.0.jar` is the closest match to what SkyyMenu's Mods section wants to become, and proves the shape works on this engine:**
  - `com.hyperessentials.gui.admin.AdminConfigPage extends InteractiveCustomUIPage` — **one generic page class edits any module's config**, not one page per module. It holds `Map settingKinds` plus an enum `SettingKind { BOOL, INT, DOUBLE, STRING, COLOR, ENUM }` — each field is described by a kind that picks its widget, the same "on/off | whole number | decimal | text | choice list" idea already in `SkyWynn-Server-Setup-Plan.md` (COLOR is a kind we hadn't listed — maybe worth adding for HUD/chat-prefix-colour settings later).
  - Edit-then-commit, not edit-on-every-click: `ConcurrentHashMap pendingChanges` / `originalValues`, `Set invalidFields`, `boolean saveConfirmActive` / `resetConfirmActive`, and a `static void clearSession(UUID)` to clean up if the player leaves mid-edit. The per-player-per-tab in-progress edit is `EditSession` (a Java record: `tab, pendingChanges, originalValues`) kept in `ConcurrentHashMap editSessions`. This is a stronger shape than "write on every click" for anything besides plain ON/OFF rows — independently echoes the sibling "Server tools" section's LuckPerms "edit safely, then commit" note above.
  - Debounce fields `long DEBOUNCE_MS` / `long lastTextInputNanos` confirm a real shipped Hytale mod hit the exact "don't rebuild the page on every keystroke" problem our TextField-plus-rebuild pattern has, and solved it by timestamping the last input and only rebuilding after a quiet gap.
  - `com.hyperessentials.gui.PageRegistry` (`registerEntry(Entry)`, `getNavBarEntries()`, `getAccessibleNavBarEntries(PlayerRef)`, `unregisterModule(String)`) is a live nav-bar registry any module plugs a page into — same idea as our bridge-based settings registry, done with plain Java interfaces because HyperEssentials is one mod (one classloader); we still need the bridge-`Function` version because Skyy mods are separate jars/classloaders.
  - `com.hyperessentials.config.ModuleConfig extends ConfigFile` (`isEnabled`/`setEnabled`, `loadModuleSettings(JsonObject)`, `writeModuleSettings(JsonObject)`) — each module owns its own JSON file and enable flag, the same per-part on/off idea `SkyyEconomy-Plan.md` already wants (bazaar/bank/auction house/NPC shops toggles).
- **`AdminUI-1.0.8.jar`** (`com.buuz135.adminui`) is separate per-feature GUIs (`BanGui`, `MuteGui`, `WarpGui`, `WhitelistGui`, `BackupGui`, `PlayerGui`, `StatsGui`), not one generic config-editor page — a fine reference for individual admin tools, not for the "any mod plugs a settings page in" architecture. Its `PermissionList` + per-action permission nodes (one node per admin action) matches our own per-node (`skyyxxx.admin`) approach rather than one all-or-nothing admin flag.
- **`roguetale-1.6.1.jar`** and **`MajorDungeons-0.4.13.jar`**: no generic config-editor page found in either, but both independently confirm the Action/Builder NPC extension point in section 3 is real and already used by other authors specifically for shop NPCs (`ActionOpenShop` → `RogueTraderShopPage`; `ActionOpenTabbedBarterShop` → `DungeonFrameworkConfigPage`) — reference only, no code copied.

**Admin commands:** none. Only player-facing `/accessories`.

**Hard-coded, not yet configurable — this is the mod with the least config in the inventory:**
- Carried-accessory slot cap: `CAP = 9` (raised from 6 in 0.2; slots 7–9 are simply blank in an older save).
- Regen tick interval for the Regeneration stat: `REGEN_EVERY = 2` seconds.
- Every rarity's stat bonus for every accessory (Vitality/Endurance/Intelligence/Regeneration/Speed etc.): flat percent-per-rarity arrays such as `[2, 4, 6, 8, 10]` for Common→Legendary, one array per accessory, entirely in Python constants.
- Every accessory's upgrade recipe (materials + quantities per rarity step, e.g. the Vitality Talisman's Common→Uncommon→Rare→Epic→Legendary material list) is generated straight into the crafting assets at build time.
- The rarity display colors are pulled from the vanilla `Server/Item/Qualities/*.json` at build time (not editable at runtime, but at least sourced from the game's own data rather than invented).

A server owner cannot today change a single accessory's power level, upgrade cost, or how many accessories a player may carry without a rebuild — this mod is the strongest candidate in this batch for a first config file once the admin config editor exists.

### Cross-mod pattern (skills / progression / island mods, this batch)

Same shape as the economy-mod batch above: one `config.properties`-family file per mod under `Skyy_<Mod>/`, `public static volatile` fields set once at `setup()`, clamped rather than rejected on bad input, and (for 8 of these 10 mods — all but **SkyySacks**, whose one setting self-polls, and **SkyyAccessories**, which has no config file at all) an explicit `/‹mod› reload`-style admin command that is the *only* way a file edit takes effect without a restart. Two things stand out that don't already show up in the economy-mod cross-mod note: **SkyyIslands 0.5 already ships the richest in-game settings experience of any mod here** (a full per-island permissions/visit-mode menu the owner edits themselves, on top of server-wide `config.properties` defaults) — proof the "click to configure in game" direction Skyy wants for SkyyMenu's Mods section is already achievable per-mod, just not yet centralized. And **zero of these 10 mods (nor, per the section above, any of the economy mods) register anything on the `settings:fn:*`/`settings:def:*` bridge** from `research/Settings-Spec.md` — not even the boolean player toggles (`/skills quiet`, `/tree quiet`, `/explore quiet`, `/collections`' own quiet-equivalent) that spec explicitly names as adoption targets for each of these mods' "next" version. The admin config editor `SkyWynn-Server-Setup-Plan.md` calls for will need a *new* bridge contract of its own (richer than booleans — whole numbers, decimals, choices, item/id lists, per-item tables) since nothing here can be wired into the existing settings registry as-is; SkyyIslands' 14-flag permission editor and SkyySkills' huge `xp.properties` are the two best existing examples of "what the richer editor needs to be able to represent" once that contract is designed.
