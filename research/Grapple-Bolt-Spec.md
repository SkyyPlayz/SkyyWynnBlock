## 0. Plain words (for Skyy)

- **Crossbow, right click = Grapple Bolt.** Click 1 shoots a rope bolt. It flies almost straight and sticks in the first block it hits.
  You keep shooting normal bolts with left click while it hangs there (your loaded bolts and reload are untouched).
- **Click 2 = pull.** Bolt stuck in a block: you are pulled fast (24 blocks/s) straight to it and stop just short of it. Bolt still
  flying (not stuck yet): you are pulled HALF way toward where the bolt is at that moment, and the bolt is gone.
- **Click 3 while being pulled = let go.** You fly on with the speed you had (plus a tiny lift), so you can shoot the next bolt and
  chain grapples. Landing after letting go = normal fall rules (you chose to fly). Landing right after a full pull = no fall damage.
- **Cost:** shooting is free (no arrows, no loaded bolts). A full pull costs 3 Stamina + 1.5 Mana, a half pull 2 Stamina + 1 Mana
  (physical = more Stamina than Mana). Too little Stamina = no pull, the bolt stays.
- **No lag by design:** the shot is the game's own predicted projectile (appears instantly); the pull is a small speed message every
  server tick (35 bytes, 30 per second, only to you) - the same way our double jump and the wand hop push you, so you are never
  teleported or snapped back. A rope line shows while the bolt flies and while you are pulled.
- **What you lose:** right click on a crossbow was the vanilla guard (block + bash). It becomes the grapple (question 1 offers
  "tap = grapple, hold = guard").
- **Dodge Roll = the vanilla dodge, everywhere.** Hytale already has a dodge key, but it only dashes left / right. We extend it to all 8
  directions with the game's own roll animations (Roll, RollBackward, RollLeft, RollRight are in the player model). Same as vanilla:
  2 Stamina, about 3-4 blocks, 0.25 s where nothing can hurt you. It is predicted by your game, so it is instant. Your Acrobatics dodge
  XP and the tree's dodge push count rolls in every direction.
- **Everything with a number is a Server Setup row** (Armory > Grapple; Skills > Acrobatics), except the few asset numbers marked
  "fixed in the jar" (the roll and the bolt flight are predicted by the game client, so they are build-time).

## 2. Engine approach per feature (evidence)

### 2.1 How a crossbow right click reaches the server (VERIFIED)
- `Template_Weapon_Crossbow.json` `Interactions`: `Primary` = `Root_Weapon_Crossbow_Primary_Signature`, **`Secondary` =
  `Root_Weapon_Crossbow_Secondary_Guard`**, `Ability1` = BigArrow, `Ability3` = reload, `SwapFrom` = the refund; **`Ability2` is free**.
  Vanilla Iron / Ancient Steel and More Crossbow Tiers (enabled in "HUD mod") all inherit it. The guard root (`RequireNewClick: true`,
  Rules Interrupting Primary) -> StatsCondition Stamina 0.5 -> `Weapon_Crossbow_Secondary_Guard_Wield` (Wielding, blocks 100 %, 7
  Stamina per damage, Primary fork = bash). Only the template names the root (Assets scan).
- The client starts the chain and sends it (`protocol.packets.interaction.SyncInteractionChains`); the server's `InteractionManager` runs
  the server-side steps. `ApplyEffect` / `EffectCondition` / `Condition` are `config/none` types (run on both sides; protocol twins
  exist), `ApplyForce` / `Charging` / `Wielding` are `config/client`. `ProjectileInteraction#firstRun` calls
  `ProjectileModule.spawnProjectile(UUID, Long, Ref, CommandBuffer, ProjectileConfig, Vector3d, Vector3d)` (bytecode 220) and the
  entity gets a `PredictedProjectile(uuid)` (spawnProjectile 311-322) -> the shot is client-predicted, no wait.
- **Clicks 2 and 3 are detected WITHOUT a custom Java interaction type** (chosen): our root chain branches on a STATE effect the server
  puts on the player, and signals clicks with a CLICK effect the server consumes:
  ```
  Root_Weapon_Crossbow_Secondary_Guard (overridden; RequireNewClick true, Cooldown 0.25):
    EffectCondition EntityEffectIds [SkyyArmory_Grapple_Out] Match All
      Next:   ApplyEffect SkyyArmory_Grapple_Click            (a click while a bolt is out / while pulling)
      Failed: DurabilityCondition > 0 -> Projectile Config SkyyArmory_Grapple_Bolt (ItemAnimationId Shoot)
  ```
  Evidence: `EffectCondition` with `EntityEffectIds` + `Match` (All / None; `protocol.Match`) is what the vanilla guard uses
  (`Stamina_Broken`, Match None); `ApplyEffect` runs server-side (the vanilla dodge's `Dodge_Invulnerability` protects on the server);
  SkyySkills `Acro.dodge` already polls effect edges every tick in production (`ecc.hasEffect(EntityEffect.getAssetMap().getIndex(..))`,
  build 0.4.16 line 8831); `EffectControllerComponent.addEffect(Ref, EntityEffect, ComponentAccessor)`, `removeEffect(Ref, int,
  ComponentAccessor)`, `hasEffect(int)` (reflect); effect assets accept `"Infinite": true` (21 vanilla effects) and `OverlapBehavior`.
  The server consumes each click by removing the CLICK effect the tick it sees it (so two clicks never merge).
- **Reload and loaded bolts stay intact (VERIFIED):** the grapple chain never touches `Ammo`, `SwapFrom` or the hotbar; the reload loop
  `Common_StatAmmoReload_Entry` is `InterruptedBy [Primary, Secondary]` - a right click stops an in-progress reload exactly as the
  vanilla guard click did; bolts already loaded stay (the `Ammo` stat is only cleared on a slot switch, Crossbow-Loaded-Spec 1.4).
  Left click (`Primary`) keeps working while a bolt waits or while you are pulled (our chain is instant, nothing stays running).
- Rejected: (a) a custom interaction type via `getCodecRegistry(Interaction.CODEC).register(name, Class, BuilderCodec)` - VERIFIED in
  GrapplingHook 2.0.2 `GrapplingHookMain#setup` and Perfect Dodges, but new to our javassist toolchain (BuilderCodec + Supplier class),
  kept as the fallback (constant CLICK_MODE = "effect" | "codec"); (b) `PlayerMouseButtonEvent` - only built in
  `InteractionModule#doMouseInteraction` (the `MouseInteraction` packet; its only listener is `CameraDemo`), not the normal click path;
  (c) server-spawning the bolt on every click (`ProjectileModule.spawnProjectile(Ref, CommandBuffer, ProjectileConfig, Vector3d,
  Vector3d)` is public) - would not be client-predicted (ping delay on the shot).
- Race (INFERRED): a second click before the client has received the OUT effect takes the shoot branch again -> `GrappleBoltSys`
  keeps only the newest bolt (removes the older one). Harmless.

### 2.2 Bolt flying vs stuck (VERIFIED)
- New-style projectile entity (crossbow bolts use `"Type": "Projectile"` + `ProjectileConfig`, not the legacy `ProjectileComponent`):
  components `Projectile`, `PredictedProjectile`, `ModelComponent`, `StandardPhysicsProvider`, `Interactions`, `DespawnComponent`
  (`ProjectileModule.DESPAWN_DELAY` = PT5M, read by reflection), Transform, Velocity, NetworkId (spawnProjectile bytecode 132-424).
- Identify ours in a RefSystem `onEntityAdded`: `ModelComponent.getModel().getModelAssetId()` == `SkyyArmory_Grapple_Bolt` and
  `StandardPhysicsProvider.getCreatorUuid()` = the shooter (both reflect).
- `StandardPhysicsTickSystem#tick`: a block impact sets `StandardPhysicsProvider.setState(STATE.RESTING)`, calls
  `RestingSupport.rest(ChunkStore, bounceBlockPosition())` and the `ImpactConsumer.onImpact(...)` with a null entity = the
  `ProjectileMiss` interactions (offsets 1600-1657); an entity hit sets `STATE.INACTIVE` + `onImpact` with the entity = `ProjectileHit`
  (1408-1444); a RESTING bolt whose support block changed goes back to ACTIVE (`RestingSupport.hasChanged`, 476-499).
  -> per tick: `getState()` ACTIVE = flying, RESTING = stuck (anchor = the bolt's Transform position, block = `bounceBlockPosition()`),
  INACTIVE or removed = gone.
- Our `ProjectileConfig` `SkyyArmory_Grapple_Bolt` (Parent `Projectile_Config_Arrow_Base`): Physics Standard, Gravity 6,
  TerminalVelocityAir 70, Bounciness 0, SticksVertically true, LaunchForce 60; `ProjectileMiss` = the impact sound only (NO
  `Common_Projectile_Despawn` and NO `Block_Break_Projectile`, unlike vanilla `Projectile_Config_Arrow_Crossbow`, which despawns after
  `Common_Projectile_Miss`'s 5 s RunTime); `ProjectileHit` = `Common_Projectile_Despawn` + a tick sound (no `DamageEntity` = no damage).
  We remove the bolt ourselves (`CommandBuffer.removeEntity(ref, RemoveReason.REMOVE)`, the 0.1.1 marker path).

### 2.3 The pull - smooth, server-driven (VERIFIED path, feel UNVERIFIED)
- Per tick for each pulling player (in SkyyArmory's existing `TravTick`, an `EntityTickingSystem` on Player, world thread, once per
  tick): `Velocity v = cb.getComponent(ref, Velocity.getComponentType()); v.addInstruction(new Vector3d(dir x speed), (VelocityConfig)
  null, ChangeVelocityType.Set)`. `PlayerVelocityInstructionSystem` sends each instruction as one `ChangeVelocity` packet
  (Magic-Traversal-Spec 2.3); the packet is FIXED 35 bytes (`ChangeVelocity.FIXED_BLOCK_SIZE`, PACKET_ID 163) -> ~1 KB/s, to the
  grappler only. GrapplingHook 2.0.2 ("smooth, Terraria-like") does exactly this every tick (`GrappleTickSystem#tick` 1457-1590:
  `addInstruction(..., Set)`, speed min(pullMaxSpeed, dist x 2.5), cap constant 24.0, y >= 0.35) - VERIFIED bytecode.
- Why per tick and not one impulse: one Set at the start flies a gravity arc that misses the anchor and needs re-aiming anyway; a
  Teleport would snap the camera and resets prediction (`TeleportAckTracker`). Positions stay client-reported (`ClientMovement`
  carries position + velocity; no server correction in the double jump / wand hop paths) -> no rubber-banding; the only delay is ping at
  the start and the end of a pull (INFERRED, test G3). Fallback constant PULL_EVERY (1 = every tick, 2 = every other tick, half the
  packets) for slow links.
- GrapplingHook also turns on temporary flight (`MovementSettings.canFly` + `SetMovementStates` packet, `GrappleFlightHelper`) to hang
  on the rope; we do NOT (no hanging state is asked for; flight toggles are a cheat surface). Gravity between two Sets (1/30 s) is
  ~1 b/s and is re-set next tick.
- Momentum on release: we stop sending and send one last Set (keep % + lift). The client then applies its normal air physics:
  `Default.json` `AirDragMin 0.96 / AirDragMax 0.995` at `AirDragMinSpeed 6 / MaxSpeed 10` (VERIFIED values; per-tick meaning INFERRED)
  -> at grapple speeds most momentum survives = "sorta fly". UNVERIFIED feel (test G5).
- Fall damage: `DamageSystems$FallDamagePlayers` uses the last |clientVelocity.y| at landing vs `MinFallSpeedToEngageRoll` 21
  (Double-Jump-Spec 1.4, VERIFIED). Pull downward speed is clamped to 18; plus a Filter-group `DamageEventSystem` (`GrappleFallSys`,
  the SkyySkills fall-reduction pattern) cancels `DamageCause.FALL` (VERIFIED enum) for a player who is pulling or inside
  `grapple.landGrace` after an arrival. Releases and snaps get no grace.
- Stamina / Mana: server-side `EntityStatMap.subtractStatValue(int, float)` on `DefaultEntityStatTypes.getStamina()` / `getMana()`
  (reflect; Zephyr's `StatUtil.tryConsume` pattern) after checking `get(int).get()`; regen pause = `setStatValue` on
  `EntityStatType.getAssetMap().getIndex("StaminaRegenDelay")` (the vanilla dodge sets it to -0.7). Server-side so the rows are live;
  the bar updates through the stat sync (~ping).
- Stall / blocked: if the distance to the target shrank less than 0.1 block over 9 ticks the pull ends as an arrival without hop.

### 2.4 Rope visual (VERIFIED APIs, look UNVERIFIED)
- Vanilla has no beam / line renderer (no Beam / Line / Ribbon shape in 1,000+ `.particlespawner` files; Trails are model-attached
  ribbons). GrapplingHook draws a chain of model entities each tick (`GrappleChainModelRenderer`) - many networked entities, rejected.
- Flight: the bolt model `SkyyArmory_Grapple_Bolt` = a build-time copy of `Server/Models/Projectiles/Weapons/Arrow/Arrow_Crude.json`
  (already has `Trails` on node Handle, TrailId `Arrow`) with TrailId `SkyyArmory_Rope_Trail` (a copy of the vanilla `Arrow` trail,
  rope brown, longer `LifeSpan`) -> the line follows the bolt for free on every client.
- Pull: `ParticleUtil.spawnParticleEffect(String, double, double, double, float yaw, float pitch, float roll, float scale, Color, Ref,
  List, ComponentAccessor, float maxDuration)` (reflect; 17 overloads) - dots of `SkyyArmory_Rope_Dot` (build-time recolour of
  `Dust_Sparkles_Fine`) every `grapple.ropeSpacing` blocks every 4 ticks. Cost: a 20-block rope = 13 dots x 7.5/s ~ 100 spawns/s per
  grappler for <= 2.5 s, `SpawnParticleSystem` >= 48 bytes each, sent only to players within `ParticleUtil.DEFAULT_PARTICLE_DISTANCE`.
  Probe P1 (game): ONE particle system rotated toward the bolt and scaled to the rope length (the yaw / pitch / scale overload) - if
  a long thin spawner scales cleanly, the rope becomes 1 packet per refresh (constant ROPE_MODE = "dots" | "stretch").
